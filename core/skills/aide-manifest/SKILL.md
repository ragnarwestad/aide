name: aide-manifest
description: >-
  Draft or refresh the project's .aide/project.yaml manifest — what the
  project IS: stack, dependencies, deployment, logging, statistics,
  reports, docs. Drafts from the codebase, ASKS about what it cannot
  derive, never guesses.
  Use when: setting up aide in a project, the manifest is stale, an
  analysis needs project context that is missing.
  Do NOT use for: per-user settings (.aide/config), creating specs
  (use aide-create), analyzing a task (use aide-analyze).
argument-hint: "[project path, defaults to the current project]"
effort: medium
---

Give the project a machine-readable identity card: `.aide/project.yaml`
in the project root. It is TEAM knowledge and belongs in git — unlike
`.aide/config`, which is personal.

**Input:** $ARGUMENTS (a project path; default: the current project root)

## Workflow

### Step 1: Establish the state

- Project root: the git toplevel of the argument or of the current
  directory
- If `.aide/project.yaml` exists: this is a REFRESH — read it, and show
  the user a diff of every change you propose before writing
- Otherwise: this is a DRAFT — start from
  `references/project.yaml` (the annotated example)

### Step 2: Derive what the codebase can tell

Read the project and fill in what is derivable:

- **stack:** build files (package.json, pom.xml, go.mod, ...), language
  mix, frameworks
- **deployment:** deploy scripts/commands, CI workflows, host config
  files (wrangler.toml, fly.toml, Dockerfile, ...). Those files often
  reveal that the host builds every branch, but rarely the exact
  address one is served on — see `deployment.preview` in Step 3
- **dependencies:** external services the code talks to (API clients,
  connection strings' KINDS — never secrets)
- **docs:** README and doc folders that exist

### Step 3: Ask about what it cannot

Log locations, statistics dashboards, report links (e.g. a Claude
artifact regenerated by a routine) are not in the code. Neither is
`deployment.preview`: where ONE branch can be tried, as a template with
a literal `{branch}` in it (`https://{branch}.example.pages.dev`). Ask
for it only when the host builds per branch, and leave it out
otherwise — a project without per-branch previews has no such address,
and the dashboard shows nothing rather than a link that 404s. Ask the
user for all of these — one compact question round, multiple-choice
where possible.
NEVER guess a URL or a location. Leave unanswered keys out rather than
inventing values.

### Step 4: Write and stamp

- Write `.aide/project.yaml` with `generated: <today>` (the staleness
  signal)
- Keep it SHORT: links over prose, no essays — if a value needs a
  paragraph, it belongs in the project's docs with a link here
- The file is committable: `git add .aide/project.yaml` (in a fresh
  project, verify `.aide/` is not swallowed by an ignore rule — only
  `.aide/config` should be ignored)
- **Leave a `worktreeLinks:` key exactly as found — never propose one,
  never remove one.** It is the dashboard's to write, and it
  names the gitignored paths a headless run symlinks into its worktree.
  Dropping it on a refresh breaks every OTHER machine's runs the next
  time they pull, while this one carries on working — a manifest is
  committed, and this key is the one thing in it that a refresh has no
  way to derive back
- **A `testScopes:` key is kept too, and this one you may ASK about.**
  It names the subdirectories that have their own test command (the
  tools-and-scripts skill, "Project commands"), so a spec runs the
  command covering what it changed instead of every command the project
  owns. Never drop one on a refresh; propose one only when the project
  visibly has a second toolchain in a subdirectory (its own lockfile or
  build file below the root), and confirm the command with the user
  rather than guessing it

### Step 5: Confirm

```text
Manifest written: .aide/project.yaml (draft)

Derived: stack, deployment, docs
From you: logging, statistics, reports
Left out (unknown): dependencies

Refresh later with /aide-manifest — consumers: /aide-analyze reads it
for project context; the aide dashboard renders it.
```

IMPORTANT:
- Never write secrets (tokens, connection strings) into the manifest
- Never guess facts you could not derive — ask or omit
- Code blocks ALWAYS end with just ` ``` `
